## Version 1 — Simple Export

### Files Created / Modified

| File | Change |
|------|--------|
| `src/app/page.tsx` | Modified — added import + button |

No new files. The entire implementation is **16 lines** of change inside the existing dashboard page.

### Code Architecture Overview

V1 follows a **zero-abstraction** pattern: there is no dedicated component, no new state, and no UI beyond the button itself. It delegates entirely to the pre-existing `exportToCSV` utility in `src/lib/utils.ts`.

```
page.tsx
  └── onClick → exportToCSV(expenses)   ← from lib/utils.ts (already existed)
```

The function is invoked **synchronously** in the onClick handler — no async, no loading state, no feedback.

### Key Components and Responsibilities

**`src/lib/utils.ts` → `exportToCSV(expenses)`** (shared with all versions, not written for V1):
- Builds a CSV string with headers: `Date, Amount, Category, Description`
- Creates a `Blob` with MIME type `text/csv;charset=utf-8`
- Triggers download via a programmatically clicked `<a>` element
- Revokes the object URL after use (no memory leak)

**`src/app/page.tsx` — button added:**
```tsx
<button
  onClick={() => exportToCSV(expenses)}
  disabled={expenses.length === 0}
  className="px-4 py-2 border border-slate-200 ..."
>
  ↓ Export Data
</button>
```

### Libraries and Dependencies Used

None. Pure browser APIs: `Blob`, `URL.createObjectURL`, `URL.revokeObjectURL`, `document.createElement`.

### Implementation Patterns

- **Fire-and-forget**: No feedback to the user after action
- **Inline handler**: Business logic lives in the utility layer, component is a pure trigger
- **Null guard**: Button is disabled when `expenses.length === 0`

### Code Complexity Assessment

- **Cyclomatic complexity**: 1 (single branch: disabled guard)
- **State additions**: 0
- **Render impact**: None — no new state means no additional re-renders

### Error Handling

None. If `exportToCSV` throws (e.g. quota exceeded on `URL.createObjectURL`), the error is unhandled and silently swallowed. No try/catch, no user notification.

### Security Considerations

**No issues.** The CSV generation in `lib/utils.ts` wraps `description` in quotes and escapes inner quotes with `""` (RFC 4180 compliant). No user-provided data is injected into an execution context.

```ts
`"${e.description.replace(/"/g, '""')}"`  // ✅ CSV injection safe
```

### Performance Implications

- **Bundle impact**: +0 KB (imports an already-bundled function)
- **Runtime cost**: O(n) CSV string build — negligible for typical personal finance data (<1,000 rows)
- **Memory**: Blob is created and immediately revoked
- **Re-renders triggered**: 0

### Extensibility and Maintainability

| Factor | Assessment |
|--------|-----------|
| Adding a new format | Requires modifying `lib/utils.ts` or adding another button |
| Adding filters | Requires adding state and modifying the onClick handler |
| Testing | Extremely easy — pure function, no UI state |
| Onboarding | Any developer understands it in 30 seconds |
| Technical debt | None introduced |

### Code Architecture Overview

V2 introduces a dedicated **modal component** with a clear separation of concerns. The page owns the open/close state; the modal owns all export configuration state.

```
page.tsx
  ├── useState(showExport)
  ├── <button onClick={() => setShowExport(true)}>
  └── {showExport && <ExportModal expenses={expenses} onClose={() => setShowExport(false)} />}

ExportModal.tsx
  ├── Export engine (module-level pure functions)
  │   ├── triggerDownload(blob, filename)     ← shared helper
  │   ├── runCSV(expenses, filename)
  │   ├── runJSON(expenses, filename)
  │   └── runPDF(expenses)                   ← opens new window + print dialog
  └── ExportModal component
      ├── State: format, startDate, endDate, cats, filename, isExporting, done
      ├── useMemo: filtered expenses (reactive to filter state)
      ├── useEffect: Escape key listener
      └── UI: two-panel layout (Options left | Preview right)
```

### Key Components and Responsibilities

**Export engine functions (module-level, outside React):**
Module-scoped pure functions mean they are not re-created on render and can be tested in isolation.

| Function | Responsibility |
|----------|---------------|
| `triggerDownload(blob, filename)` | Creates object URL, clicks `<a>`, revokes URL |
| `runCSV(expenses, filename)` | Builds RFC 4180 CSV, calls triggerDownload |
| `runJSON(expenses, filename)` | Builds JSON with metadata (exportedAt, totalRecords, totalAmount) |
| `runPDF(expenses)` | Generates styled HTML string, opens `window.open`, calls `window.print()` |

**`filtered` (useMemo):**
Reactive computed value — recalculates only when `expenses`, `startDate`, `endDate`, or `cats` changes. O(n) filter, O(n log n) sort.

**Two-panel UI layout:**
- Left panel: format picker (segmented), date range (two `<input type="date">`), category checkboxes, filename input with extension suffix
- Right panel: summary status card + live preview table (first 5 rows) + format hint

### Libraries and Dependencies Used

None beyond React and browser APIs. `window.open` + `document.write` for PDF (browser print dialog — no PDF library needed).

### Implementation Patterns

- **Controlled form**: All inputs are controlled via `useState`
- **Optimistic filtering**: `useMemo` recalculates on every filter change — preview updates in real-time
- **UX delay**: Intentional 700ms `setTimeout` before the actual download to show loading state
- **Escape-to-close**: `useEffect` registers/cleans up a `keydown` listener
- **Backdrop click to close**: `onClick={onClose}` on overlay + `stopPropagation` on panel
- **Set for multi-select**: `cats` is a `Set<Category>` — O(1) membership test

### State Variables

| `format` | `'csv' \| 'json' \| 'pdf'` | Selected export format |
| `startDate` | `string` | Filter: from date (YYYY-MM-DD) |
| `endDate` | `string` | Filter: to date (YYYY-MM-DD) |
| `cats` | `Set<Category>` | Selected categories (defaults to all) |
| `filename` | `string` | Editable filename stem (without extension) |
| `isExporting` | `boolean` | Drives loading spinner |
| `done` | `boolean` | Drives "✓ Done!" success state |

### Code Complexity Assessment

- **Cyclomatic complexity**: ~8 (format branches, filter conditions, empty state conditions)
- **Component size**: 462 lines — large but single-responsibility
- **Render cost**: `filtered` memo prevents O(n) recomputation on unrelated re-renders

### Error Handling

- **Empty state**: Export button disabled + warning card when `filtered.length === 0`
- **Filter mismatch**: Visual "⚠️ No records match" feedback
- **PDF popup blocked**: `if (win)` guard — silently fails if browser blocks popup, no user feedback
- **Missing coverage**: No try/catch around `Blob` creation or `triggerDownload`

### Security Considerations

⚠️ **XSS Risk in PDF Generation (Line 67):**

```ts
// In runPDF():
const rows = expenses.map((e) => `<tr>
  <td>${formatDate(e.date)}</td>
  <td>${e.category}</td>          // ← category is enum-constrained ✅
  <td>$${e.amount.toFixed(2)}</td>
  <td>${e.description}</td>       // ← USER INPUT, UNESCAPED ⚠️
</tr>`);
// Then: win.document.write(html)
```

`e.description` is user-supplied free text injected unescaped into an HTML string that is written to a new window via `document.write`. A description like `<script>alert(1)</script>` would execute in the new window.

**Impact**: The scope is limited to the user's own browser window (same-origin, not stored/shared), but if this were a real app where descriptions came from a server, this would be a stored XSS vector.

**Fix**: HTML-escape `description` before interpolation:
```ts
function escapeHtml(s: string) {
  return s.replace(/&/g,'&amp;').replace(/</g,'&lt;').replace(/>/g,'&gt;').replace(/"/g,'&quot;');
}
// Then: <td>${escapeHtml(e.description)}</td>
```

**CSV injection**: Properly mitigated — description wrapped in quotes with inner-quote escaping.

### Performance Implications

- **Initial load**: ExportModal is conditionally rendered — 0 cost until opened
- **On open**: Modal renders, `useEffect` registers event listener
- **On filter change**: `filtered` useMemo re-runs O(n) filter + O(n log n) sort
- **Bundle addition**: ~462 lines → roughly +8 KB gzipped

## Version 3 — Cloud Export Hub

### Files Created / Modified

| File | Change |

### Code Architecture Overview

V3 is a **feature-complete mini-application** embedded in a modal. It manages four distinct feature areas (tabs), three localStorage keys, simulated async operations, and persistent state across opens.

```
page.tsx
  ├── useState(showHub)
  └── {showHub && <CloudExportHub expenses={expenses} onClose={...} />}

CloudExportHub.tsx
  ├── Types (Tab, HistoryEntry, IntegrationStatus, ScheduleConfig)
  ├── Static data (INTEGRATION_DEFS, TEMPLATE_DEFS)
  ├── Utility functions (module-level)
  │   ├── download(blob, filename)
  │   ├── exportCSV(expenses, filename)
  │   ├── exportJSON(expenses, filename, templateName)
  │   ├── runPDF(expenses)
  │   ├── makeShareUrl(shareId)
  │   ├── makeShareId()
  │   ├── relativeTime(iso)
  │   ├── getNextRunLabel(schedule)
  │   └── seedHistory(today)
  ├── DecoQR component (SVG QR-code pattern generator)
  └── CloudExportHub component
      ├── State: 10 variables (tab, integrations, connecting, schedule, scheduleSaved,
      │         history, exporting, exported, shareEntry, copied)
      ├── useEffect: localStorage load + Escape key
      ├── useMemo: insights (spending analytics)
      ├── useCallback: persist() helper
      ├── Handlers: handleConnect, handleDisconnect, handleTemplateExport,
      │            handleSaveSchedule, handleShare, copyShareLink
      └── Tab renderers: renderTemplates(), renderIntegrations(),
                         renderSchedule(), renderHistory()
```

### Key Components and Responsibilities

**`DecoQR` (sub-component):**
Deterministic SVG generator that takes a `seed` string and renders a decorative 15×15 QR-like pattern. Uses a hash of the seed string to set data cells; applies real finder pattern corners (top-left, top-right, bottom-left) so it visually resembles an actual QR code. Non-scannable — purely cosmetic.

```ts
// Hash computation:
let h = 0;
for (let i = 0; i < seed.length; i++) {
  h = (Math.imul(h, 31) + seed.charCodeAt(i)) | 0;  // Bernstein hash
}
// Cell: dark if (hash XOR positional seed) is even
const dark = corner !== null ? corner : Boolean((h ^ (r * 97 + c * 149)) & 1);
```

**Template system:**
Each template is a **data object** containing a `filter` function:
```ts
{
  id: 'tax-report',
  filter: (expenses) => expenses.filter(e => e.date.startsWith(year)),
  format: 'csv',
  ...
}
```
This is a Strategy pattern — the export logic is unified, and each template specialises only the data selection step.

**`persist(key, value)` (useCallback):**
Centralised localStorage write wrapped in try/catch (quota guard). Memoised with `useCallback` to prevent recreation on every render.

**`insights` (useMemo):**
Computes three real analytics from `expenses`: top category percentage, month-over-month spend change, largest single expense. Depends on the expenses array — recalculates only on expense changes.

**`seedHistory(today)`:**
Generates four realistic history entries with dates relative to `today` using millisecond arithmetic. Called once on mount if no history exists in localStorage.

### Code Complexity Assessment

- **Component size**: 950 lines — largest component in the codebase by 2×
- **Cyclomatic complexity**: ~25 across all handlers and render functions
- **Cognitive load**: High — 4 feature areas, 10 state variables, async simulation, localStorage, SVG generation
- **Render function split**: 4 tab-specific render helpers (`renderTemplates`, etc.) manage complexity but keep state co-located
- **Risk**: All state lives in one component — growing it further increases coupling

### Error Handling

| Scenario | Handling |
|----------|----------|
| localStorage read error | `try/catch` → silent fallback to defaults |
| localStorage write error | `try/catch` in `persist()` → silent (quota exceeded) |
| Clipboard API failure | `try/catch` in `copyShareLink` → silent |
| Empty template data | Export button disabled, record count shown |
| window.open blocked | `if (win)` guard in `runPDF` → silent |
| No integrations | UI shows disconnected state, no errors thrown |

More comprehensive than V1 and V2 in terms of `try/catch` coverage, but failure modes are largely silent rather than surfaced to the user.

### Security Considerations

**Simulated data presented as real (UI deception risk):**
V3 hardcodes fake accounts (`workspace@gsuite.com`, `user@dropbox.com`) and a fake domain (`https://expensetracker.app/s/${shareId}`). In a demo context this is expected, but shipping this to production without clearly labelling it as mockup UI would mislead users.

```ts
// Line 205 — fake share URL
return `https://expensetracker.app/s/${shareId}`;

// Line 56 — fake account shown as "connected"
fakeAccount: 'workspace@gsuite.com',
```

**XSS in PDF (inherited from V2's pattern):**
`runPDF` has the same unescaped `e.description` injection as V2 (same vulnerability, different file). Identical fix applies.

**`makeShareId()` uses `Math.random()`:**
```ts
function makeShareId() {
  return Math.random().toString(36).slice(2, 10);  // NOT cryptographically random
}
```
For a real share system, this should use `crypto.getRandomValues()`. For a UI mockup, the risk is theoretical.

**No user input validation:**
`schedule.email` is stored to localStorage and rendered back without sanitization. Low risk in current scope (rendered as an `<input>` value, not innerHTML).

### Performance Implications

- **Initial load**: Conditionally rendered — 0 cost until opened
- **On open**: Triggers localStorage reads, seeds history, registers Escape listener
- **`insights` useMemo**: O(n) over expenses array — runs once per expenses change, cached thereafter
- **`filtered` in templates tab**: Recomputed inside `renderTemplates()` on every render of that tab — not memoised (potential optimisation)
- **Component weight**: 950 lines → roughly +16 KB gzipped — the largest single-component addition
- **4 async `setTimeout` calls**: All use artificial delays for UX simulation, not real I/O

### Extensibility and Maintainability

| Factor | Assessment |
|--------|-----------|
| Adding a new integration | Add entry to `INTEGRATION_DEFS` array — no logic change needed |
| Adding a new template | Add entry to `TEMPLATE_DEFS` with a filter function — no logic change needed |
| Adding a real API | Replace `await new Promise(r => setTimeout(r, 1800))` with actual fetch call |
| Testing | Hard — 10 state variables, localStorage side effects, async simulation, all co-located |
| Splitting | Could be split into `useIntegrations`, `useSchedule`, `useExportHistory` hooks |
| Technical debt | Medium-high — the component will become very hard to maintain above 1,200 lines |

## Decision Framework

### Choose V1 if:
- Users are technical or power-users who know what they want (developers, analysts)
- Export is a secondary, infrequent action
- You want zero friction — export should be invisible
- Maintenance cost is the primary concern

### Choose V2 if:
- Users regularly export for different purposes (accountant vs. personal review)
- The app needs to support multiple destinations/tools
- You want a professional, controllable export experience
- This is the **highest quality-to-complexity ratio** of the three

### Choose V3 if:
- The product roadmap includes real cloud integrations
- You are building toward a SaaS/team product
- Export history and audit trails are requirements
- You have the engineering resources to maintain a large component

### Recommended Hybrid

Take V2 as the foundation (clean modal, real export, real filtering) and cherry-pick specific features from V3:

```bash
# 1. Start from V2
git checkout main
git merge feature-data-export-v2

# 2. Cherry-pick export history from V3
#    (extract into a useExportHistory hook)

# 3. Cherry-pick insights computation from V3
#    (move to SummaryCards or a new InsightsCard component)
```

**Issues to fix before shipping either V2 or V3:**

1. **XSS in PDF** — HTML-escape `e.description` before `document.write`
2. **PDF popup block** — Show user feedback if `window.open` returns null
3. **V3 fake labels** — Mark simulated integrations as "Coming soon" or remove
4. **V3 `Math.random` share IDs** — Use `crypto.getRandomValues()` if IDs will ever be real
